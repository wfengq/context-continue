# 核心库：补上三个信息缺口

- 日期：2026-11-02
- 状态：待审阅
- 上游：`2026-10-11-group-context-layer-design.md`（第 4、5.2、6 节）、`2026-10-31-bench-long-scenarios.md`
- 起因：长剧本评测中，C 组费用最低，但关键信息可见率只有约 63%（标准剧本 29%），其他多 Bot 组 90–100%。最终评审确认原因是核心库的三个缺口（见 `packages/core/README.md` "Known gaps"），不是评测误差。

## 1. 目标

在不明显增加 C 组费用的前提下，把 C 组的关键信息可见率提到与其他组相当的水平（目标：长剧本 ≥ 90%）。改完重跑评测，如实报告费用与可见率的变化。

## 2. 缺口与改法

### 2.1 没有 @ 的人类消息到不了负责人

现状：人类消息未 @ 时，只叫醒匹配到的工作块负责人；负责人自己不负责任何工作块时，它的简报增量里也看不到这条消息（`brief.ts` relevantEntries 只按 @、回复、自己工作块匹配过滤）。

改法：
- 负责人的增量包含所有人类发的聊天消息（负责人协调全部工作，与 R33 对交付、阻塞事件的处理一致）。
- 叫醒规则不变（不额外叫醒负责人，避免增加请求次数）。

### 2.2 只看过一次就被折叠

现状：契约、决定、失败记录在简报里完整显示一次后记为"已看过"，之后只显示 id 与标题。如果那一次是 Bot 被叫醒后什么都没做的请求，之后真正干活时就看不到内容了。

改法：两阶段"已看过"。
- `buildBrief` 把本次新显示的条目记为"待确认"，不立即并入已看过。
- 该 Bot 之后调用任意工具（`callTool`）时，把待确认的条目并入已看过。
- 下一次简报前没有任何工具调用（空转请求），待确认条目作废，下次照样完整显示。
- `peek` 行为不变。

### 2.3 负责人审查时看不到该工作块的失败记录

现状：核心库有 `reviewContext`（设计文档第 4 节），但内容只有交付物、契约、约定、决定，没有失败记录与事实；评测的 C 组审查时用的是普通简报，而负责人通常不负责该工作块，投影里也没有它的失败记录。

改法：
- `reviewContext` 增加被审工作块相关的失败记录与事实。
- 评测 C 组：审查步骤改用 `reviewContext`，重新拆分步骤改用 `planningContext`（核心库为这两种场景设计的上下文，包含全部人类消息与上一份计划）。请求内容即这些上下文的段，可缓存部分按统一规则（R-B19）。

## 3. 评测

- 改完后重跑五个剧本六组，报告前后对比（费用、可见率、每条事实可见率）。
- 预期：C 组改需求类与失败类事实可见率明显上升；费用会上升，需如实报告。
- 不为 C 组修改剧本或评测规则。

## 4. 不做

- 无模型时把人类消息自动抽取到项目板（需要抽取模型，留到真模型阶段）。
- 改变叫醒规则。
