# 估算：只追加的简报流 + 按影响范围分发

- 日期：2026-11-05
- 状态：已估算
- 上游：`2026-11-04-xlong-scenario.md` 第 6 节、`2026-11-04-project-wide-board.md` 第 6 节

## 1. 问题与目标

现有结果是取舍而非质变：C 组单次上下文小 10 倍以上，但每次重新拼简报，项目板一变后面全部重新计费，有缓存时短、中项目不比 D/E 便宜；按"属于谁的工作块"裁剪又漏掉全项目都该知道的事实。

本文是**估算**，不改核心库：在评测里写一个原型策略，用核心库的公开数据（项目板、账本、简报）重新组织 C 组每次请求的内容，回答——

> 能否在三档剧本上**同时**比 D、E 便宜，并且关键信息可见率 ≥ 95%？

结论决定是否正式改核心库；若不能，转向用真模型衡量质量。

## 2. 原型策略（`--c-stream`）

C 组照常调用核心库（叫醒、工具、审查与拆分完全不变），只改"每次请求发给模型的文字"：

- **只追加的流：** 每个 Bot 有一条请求文字流。首次请求发送一次**快照**；之后每次请求只在末尾追加新内容，前面的内容逐字节不变（因此按统一缓存规则 R-B19 几乎全部可缓存）。
- **快照内容：** 公共说明、该 Bot 的记忆与工作区、项目板（目标、约束、约定、工作块，以及第 2.1 节的全项目信息全文）、该 Bot 的投影。
- **每次追加：** ①自上次以来新出现或变化的**全项目信息**（第 2.1 节）；②核心库简报中该 Bot 的增量段（与它相关的新消息、交付、审查结果）；③触发说明（任务行）。
- **重新快照：** 当快照之后追加的内容超过 `restreamTokens`（默认 8,000）时，下一次请求改发新快照（这一次缓存失效）。取 4,000 / 8,000 / 16,000 三档报告敏感度。
- 审查与拆分请求：沿用核心库的审查/拆分上下文正文，作为追加内容放在流末尾（不另起前缀）。

### 2.1 按影响范围分发

以下视为**全项目信息**，追加给所有 Bot（每条只追加一次，内容变化时追加新版本）：

- 人类发的所有聊天消息（不再受 `directivesKeep` 的 20 条限制；超过后由重新快照收拢进项目板快照）；
- 约定、接口约定（含规格原文）、失败记录、决定（含理由）；
- 工作块状态变化（一行）。

只与某个 Bot 有关的内容（上游交付全文、针对它的消息与审查结果）仍按核心库的相关性规则，只给相关的 Bot。

## 3. 评测与输出

- 命令行 `--c-stream off|on`（默认 `off`，行为与现在完全相同），`on` 时报告参数记录 `restreamTokens`；可用 `--restream-tokens <n>` 调整。
- 测量变体 `--c-stream-own on`（只能与 `--c-stream on` 一起用，默认 `off`）：每个 Bot 的脚本化回复与工具调用行按 E 给作者看的格式（`src/text.ts` 的 `fmtBot` 与 `fmtOps`）在它的请求之后追加到它的流中，计入重新快照预算，快照不带它们；用来衡量"流里没有自身输出"这一差别（第 5.2 节）。
- 对三档全部剧本运行：`off`、`on`（4k / 8k / 16k），报告 C 组费用、可见率、单次请求中位数与最大值，与 D、E 对比；其他组结果必须不变。
- 结果写入本文第 5 节，回答第 1 节的问题；不改核心库，不写推荐默认值以外的结论。

## 4. 风险

- 只追加的流会随时间变长：单次请求变大（但仍远小于聊天历史，因为只含筛选后的内容并定期重新快照）。
- 全项目信息全部追加给所有 Bot，可能让小团队的短剧本反而更贵。
- 原型在评测里拼文字，结果代表"如果核心库这样输出"的上限估计，正式实现时格式会不同。

## 5. 结果

运行方式：`pnpm -C packages/bench bench run --scenario all --group all --out <目录> --stamp T`，分别加 `--c-stream off`，以及 `--c-stream on --restream-tokens 4000`、`8000`、`16000`（六个剧本、六组，输出到仓库外的目录）；`on 8000` 运行两次。另以 `--c-stream on --c-stream-own on --restream-tokens 4000`、`8000`、`16000` 测量"流中带 Bot 自身输出"的变体（第 5.2 节；`8000` 运行两次）。核对结果：

- A、B、D、E、F 在全部七种设置下的全部指标与全部请求记录完全相同（`results.json` 中非 C 组的 `metrics` 与 `records` 逐项相等）；报告中除 C 组的行、各逐事实表中的 C 列、`cStream` 参数行与流模式说明外完全相同。流模式下报告还有三处不同：不打印各剧本的 C 组"上限"行（流内各段都按已标记可缓存处理）；"可缓存"说明改为"前缀规则单独决定"；不打印超长档的 `directivesKeep`（只保留最新 20 条人类消息）说明（流不受该限制）；
- C 组在每种设置、每个剧本中核心错误均为 0，全部收尾；
- `on 8000` 两次运行、`on 8000` 加自身输出两次运行的 `results.json` 与 `report.md` 各自逐字节相同（`cmp`）；
- 每次运行约 10–11 秒（不含构建），远低于 300 秒；
- 下文"重新快照"次数、第 5.3 节的漏看分类与三种可见率口径不是评测报告的输出，而来自在仓库外用已构建的评测（`dist/`）重放 C 组的脚本：它包装 `ctx.call`，记录每次请求的分段文字与当时的项目板，核对得到的命中与机会数与 `results.json` 逐剧本一致。

### 5.2 回答第 1 节的问题

> 能否在三档剧本上同时比 D、E 便宜，并且关键信息可见率 ≥ 95%？

**按剧本的事实定义、流里不带 Bot 自身输出时部分能：长档能，超长档在 8k、16k 勉强能，标准档不能。把 Bot 自身的输出也放进流（D、E 的历史都带）后，没有一种预算能同时让长档和超长档满足两个条件，默认预算 8,000 下三档都不满足。**

| 档 | 不带自身输出（`--c-stream on`） | 带自身输出（`--c-stream-own on`） | 依据 |
|---|---|---|---|
| 标准 | 否 | 否 | 可见率三种预算都与 D、E 相同（95.7%）；费用不带时高约 19%–22%，带时高约 45%–54%。 |
| 长 | 是（三种预算） | 只有 4k | 不带：比 D 便宜 16%–23%、比 E 便宜 12%–19%，可见率 98.8%–99.8%，高于 D（98.1%）、E（97.7%）。带：4k 比 D、E 便宜 9.3%、5.0%（可见率 99.1%）；8k 比 D 便宜 2.2%，但比 E 贵 2.4%；16k 比两者都贵。长档没有被撤下的契约，第 5.3 节的三种口径相同。 |
| 超长 | 是（8k、16k），按剧本的事实定义；4k 否 | 只有 16k，按剧本的事实定义 | 不带：便宜约 75%–80%；8k 可见率 96.0%，只高出 95% 1.0 个百分点，且依赖撤下的契约在下次快照前仍留在流中；若撤下即收回，8k 为 92.8%、16k 为 94.3%、4k 为 91.9%，三种预算都低于 95%。带：便宜约 70%–76%；8k 可见率降到 94.6%，16k 为 96.5%（撤下即收回时 94.3%）。 |

上表的适用范围：

- **只回答费用与字面可见。** 费用是上下文费用（R-B19 前缀缓存规则，`--cache-ratio 0.1`），可见率是标记文字是否出现在请求中；模型是脚本化的假模型，不衡量 Bot 是否用上了这些信息，也不衡量输出质量与一致性。
- **"不带自身输出"一列是节省的上限。** 这一列与 C `off` 一样，流里没有 Bot 自己的回复与工具调用，而 D、E 的历史都带。"带自身输出"一列按 E 的作者格式（回复、带参数的工具行、交付全文）把它们追加到流中，数字见第 5.1 节各表的"+ 自身输出"行。若只带 D 那样的简短格式（工具行不带参数，交付只给引用；评测没有这个开关，是用临时改过的构建在 8k 下测的一次），长档比 D、E 便宜 13.9%、9.8%（可见率 100%）；超长档便宜 77.5%、75.2%，可见率 95.2%（撤下即收回时 93.0%）。真实聊天接口里，Bot 自己的工具调用带全部参数，更接近 E 的格式。
- **超长档的"是"取决于第 5.3 节的设计问题。** 三种口径的可见率见第 5.3 节。

结论：默认预算 8,000 只在"不带自身输出、按剧本的事实定义"时同时满足长档与超长档。带上自身输出后，长档只有 4k 满足，超长档只有 16k 满足。没有一种设置能让标准档比 D、E 便宜。

product-plan、event-plan 没有漏看；long-app 在 8k、16k 下没有漏看。

- **项目板条目被重新拆分撤下**（超长档的主要来源）：这些标记是计划中的契约（`error-envelope`、`session-tokens`、`doc-roles`、`entitlements`、`dunning-states`、`state-vector-resync`、`export-jobs`），曾以项目板条目的形式进入该 Bot 的流；之后的重新拆分（第 196、381、575、753、945 步等阶段性重拆）提出的新计划不再包含它们，核心库把它们从项目板上撤下。流会追加一行 `removed from the board`，但原文仍留在前缀中，直到下一次快照；新快照按当时的项目板生成，正确地不再包含它们。因此预算越小、重新快照越频繁，漏看越多（1,144 / 591 / 381）；超长档三种预算之间的可见率差别**全部**来自这一类（其余漏看三种预算都是 62 次）。这些漏看在 C `off` 中全部同样漏看（4k、8k、16k 各 1,144 / 591 / 381 次，逐次核对）。
- **增量中见过、重新快照后丢失**（只在 4k 的长档）：Bot 之间在聊天中约定、没有成为项目板条目的内容，按核心库的相关性规则进入过该 Bot 的增量或触发说明；快照不含 Bot 聊天，下一次快照后它就不在流中。8k、16k 下没有出现这类漏看。
- **Bot 自己的消息**：标记出现在该 Bot 自己发出的消息或工具调用中（例如 backend 发出的 `error-envelope` 约定），C 组（`off` 与默认的流）都不把 Bot 自己的输出放回它的请求；`--c-stream-own on` 放回后，超长档 8k 下这类漏看从 38 次降到 4 次（剩下 4 次未逐一核对，可能是重新快照后流中不再有那条自身输出）。
- **从未送达**：Bot 聊天中的约定，核心库的相关性规则从未把它送给这个 Bot（flappy-bird 中 coder 只发给 artist；xlong 中 qa 不在消息的相关范围内）。按第 2.1 节，Bot 聊天不属于全项目信息，这是设计的结果。

由此引出一个未决的设计问题：**工作块结束、契约被新计划撤下之后，它是否仍应对相关 Bot 可见？** 剧本的事实定义认为应该（受众从事实出现起始终应看到），D、E 因为保留全部历史而看得到；项目板认为不应该（撤下即不再适用）。流在两者之间：撤下后到下一次快照前仍看得到。超长档的可见率在多大程度上满足 95%，取决于这个问题的答案，下面按三种口径给出。

**三种可见率口径。** 称一次机会的事实为"已撤下"：请求时，它的标记出现在某个曾在项目板上、现已撤下的条目（主要是契约）的文字中，且不出现在当前项目板的任何条目中。项目板由核心库决定，与流无关，因此超长档每种设置都有 3,096 次这样的机会（C `off` 也一样）。对其中的命中，去掉请求中所有提到已撤下条目的行（`[id]`、`[id@vN]`、计划行 `contract <id> …` 及其续行）后标记不再出现的，称为"只靠撤下后留下的文字命中"；标记在别处（人类消息、交付、聊天增量等）仍出现的，照常算命中。

- (a) 现行：评测报告的口径（剧本的事实定义）。
- (b) 撤下即不再适用：已撤下事实的机会中，漏看的和只靠留下文字命中的都不计入机会。
- (c) 撤下即收回：机会照常，只靠留下文字的命中算漏看。

|---|---:|---:|---:|---|
| C off | 63.5%（10391/16364） | 70.8%（10391/14681） | 63.5%（10391/16364） | 1,683 / 0 / 1,413 |
| C on 4k | 92.6%（15158/16364） | 99.6%（15046/15108） | 91.9%（15046/16364） | 1,144 / 112 / 1,840 |
| C on 8k | 96.0%（15711/16364） | 99.6%（15189/15251） | 92.8%（15189/16364） | 591 / 522 / 1,983 |
| C on 16k | 97.3%（15921/16364） | 99.6%（15429/15491） | 94.3%（15429/16364） | 381 / 492 / 2,223 |

由此：(b) 口径下三种预算都约 99.6%，彼此接近，C 超长档轻松满足 95%；(c) 口径下三种预算都不足 95%（最高 16k 的 94.3%），即使带上自身输出也一样。8k 在 (a) 口径下的 96.0% 中，有 522 次命中只来自撤下后仍留在流中的旧契约文字；而 8k 只比 95% 多约 165 次命中，所以去掉这些命中后为 92.8%。

### 5.4 对正式实现的含义

原型在评测里拼文字；若正式实现，需要核心库提供以下能力，而不是让宿主解析核心库的输出文字：

- **每个 Bot 一条只追加的流**：核心库为每个 Bot 记住"流里已经显示过什么"（项目板条目的 id 与版本、人类消息序号、记忆与投影的各条目），每次请求返回"本次快照"或"只追加的部分"，并保证追加时前缀逐字节不变。原型由宿主维护这些状态，并为此把每条消息与项目板都读一遍。
- **快照 / 重新快照策略**：按追加的 token 数决定何时重新快照。本次结果中，不带自身输出时 8,000 在长档、超长档同时满足两个条件（超长档只按剧本的事实定义，余量 1.0 个百分点）；4,000 在超长档可见率不足，16,000 更贵且最大请求达 23k。带自身输出时没有一种预算同时满足长档和超长档（第 5.2 节），所以这个预算还不能作为推荐默认值。重新快照落在审查或重新拆分请求上时，需要一份不改变状态的简报（原型用 `buildBrief(..., { peek: true })` 取记忆、笔记与投影）。撤下的条目在流中保留到下次快照，这一行为需要与第 5.3 节的设计问题一起决定：撤下即收回（追加一行收回说明还不够，旧文字仍在前缀里）要么接受第 5.3 节 (c) 口径的可见率，要么在撤下时提前重新快照，代价是更多缓存失效。
- **Bot 自身的输出**：真实的聊天接口里，Bot 自己的每一轮（回复与带全部参数的工具调用）都会作为助手消息留在它的会话中；原型的"不带自身输出"相当于宿主每次丢掉它们。按 E 的作者格式带上之后，C 的费用高 16%–26%，长档在 8k 下不再比 E 便宜（第 5.1、5.2 节）。正式实现要决定自身输出的格式与去留：完整保留（贵）、只保留简短格式（D 那样不带参数、交付只给引用，8k 下长档便宜 13.9% / 9.8%，超长档可见率 95.2%）、或在重新快照时并入项目板与笔记（原型的快照不带它们）。
- **缓存的真实行为**：R-B19 只按"与该 Bot 上一次请求逐段相同的最长前缀"计算，没有建模缓存过期（例如数分钟不用即失效。评测的步与真实时间没有对应关系；超长档中同一 Bot 两次请求之间中位数隔 6 步、最长 48 步，若间隔超过缓存寿命，空闲 Bot 的下一次请求实际上要全部重新计费）、单次请求可设的缓存断点数量限制、以及首次写入缓存的额外费用。流越长、Bot 越空闲，这些因素对 C 越不利；D、E 同样受影响，但它们的请求更大。
- **快照随人类消息增长**：每次快照都带全部人类消息（不受 `directivesKeep` 限制）。本次剧本最多 37 条（超长档约 2.1k token），尚可接受；更长的项目需要上限，或"把已体现在项目板上的人类消息并入项目板条目、快照只带未并入的"规则。
- **按小节、按工作块的逐行更新**：原型的 `sectionUpdate` 对记忆、笔记、投影做逐行比较，依赖核心库的渲染约定：`#` / `##` 标题、两个空格的续行、`- [key]` 条目、` (seen)` 后缀、笔记标签（`Persona:`、`Pinned:`、`Recent:` 等）、`# Your part` 块中的工作块行。任何格式变化都会让更新错归或重复。核心库应直接给出结构化数据：投影按（工作块、小节、条目 id、版本）列出，记忆与笔记按条目列出，"已读压缩"是条目上的标记而不是文字后缀，并提供"自某个游标以来新增 / 变化 / 删除了哪些条目"的接口，以及只渲染单个条目或单行更新的函数。
- **全项目信息的变更**：原型通过比较两次 `board()` 的渲染文字发现变化；核心库应按 id 与版本给出项目板变更事件（新增、改版、撤下），人类消息按序号读取（原型已用账本的 `read(projectId, seq)`）。
- **增量与项目板条目同样依赖文字格式**：除 `sectionUpdate` 外，原型的 `trimDelta` 按核心库增量中聊天行的文字格式（`- #<seq> <author> (id: <id>): …`）删去流已带的人类消息，`projectWide` 按核心库 `render.ts` 的字段布局重新渲染约定、契约、决定、失败与工作块。核心库改动任一格式，原型就会重复或漏掉内容。核心库应给出结构化的增量条目（类型、账本 id、序号、作者、正文），并导出渲染单个项目板条目的函数。
- **团队名单**：原型中公共段（团队名单）在两次快照之间冻结，重新拆分新增的成员只通过工作块更新到达旧流；正式实现应把名单变化也作为追加事件。

### 5.5 注意事项

- 结果来自脚本化的假模型，只衡量上下文大小与标记的字面可见，不衡量质量；可见率按标记文字匹配，流在撤下后仍保留的旧条目文字也算"可见"。
- 默认的流不包含 Bot 自己的回复与工具调用（与 C `off` 相同），而 D、E 都带；带上之后的费用与可见率见 `--c-stream-own on` 的结果（第 5.1 节"+ 自身输出"行、第 5.2 节）。
- 公共段（团队名单）、以及快照中的记忆与工作区在两次快照之间不重发，只追加变化的行；团队名单不追加。
- 费用按 R-B19 的前缀缓存规则计算，流内各段都按"核心库标记可缓存"处理；工具定义在各组都不计入。
- 超长档上 A、B 的单次请求超过 128,000 token 的窗口，它们的数字假定窗口无限，不可直接比较（本节只与 D、E 比较）；E 在超长档压缩一次，压缩摘要假定保留全部标记（对 E 有利）。
- 原型的结果代表"如果核心库这样输出"的估计；正式实现的格式不同，费用与可见率会随之变化。
