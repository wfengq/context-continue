# 真模型重放：整个项目的真实费用与缓存

- 日期：2026-11-07
- 状态：待实现
- 上游：`2026-11-07-real-model-probes.md`（真模型问答，§5.3 发现问答请求稀疏、真实缓存命中低于估算）、`2026-11-06-core-stream-mode.md`（长项目模式）

## 1. 目标

问答评测只在少数时刻发请求，真实缓存命中（C 组超长档 69%）明显低于评测的缓存估算（95%），但那不代表完整运行。本评测回答：

> 把每一组在整个项目里的**每一个请求**都按原顺序发给真模型，真实费用和缓存命中是多少？C 组相对 D、E 的费用比例是否与评测估算（R-B19）一致？在真实的缓存状态下，关键事实问答的答对率是否不变？

## 2. 方法

- **新参数 `--replay`**：与 `--probes` 一样启用真模型设置（`--provider`、`--model`、`--base-url`、`--api-key-env`、`--price` 或内置价目、`--thinking`、`--dry-run`、`--max-cost`），两者可单独或同时使用；问题相关的参数（`--probe-groups`、`--probe-samples`、`--max-probes`、`--no-probe-control`）仍只与 `--probes` 一起用。重放的组即 `--group` 选中的组。剧本仍由脚本驱动，各组面对的是同一个项目进程。
- **每个请求都发给真模型：** 剧本请求与 Bot 被叫醒的额外请求，按运行顺序逐个发送，段内容与评测记录的完全相同（与 probe 用同一个适配器，同样的缓存断点规则）。
- **回答记录后丢弃：** 真模型的回答只用于记录用量，不进入项目；剧本请求仍返回剧本中的回复，额外请求仍返回固定的空闲回复。因此不加 `--replay` 时与现在逐字节相同，加 `--replay` 时剧本请求的记录（`CallRecord`）也与不加时相同，真模型用量单独记录。
- **输出上限：** 重放请求的 `max_tokens` 为 16（只衡量输入与缓存；报告注明输出费用不代表真实回复）。probe 问题仍为 200。
- **问答随行：** 加 `--probes` 时，问题在其预定时刻、紧跟该剧本请求之后发送，与重放请求在同一顺序里，因此缓存状态与真实使用一致。无上下文对照照常。
- **组的运行顺序：** 与现在相同（逐组）；用户也可以每组一个命令并行运行（不同组的前缀不同，缓存互不复用）。

## 3. 报告

每个剧本、每组一行：

| 字段 | 含义 |
|---|---|
| 请求数 | 实际发出的重放请求（剧本 + 额外） |
| 未缓存 / 缓存写 / 缓存读 / 输出 token | 服务商返回的用量 |
| 真实费用 | 按价目计算 |
| 真实缓存读 % | 缓存读 ÷（未缓存 + 缓存写 + 缓存读） |
| 估算可缓存 % | 评测按 R-B19 的估算（同一组请求） |
| 估算费用单位 | 现有的 cost units |

另有对照表：以 D、E 为基准，C 的**真实费用**比例与**估算费用单位**比例并列（例如超长档估算 −72% / −70%），每档一张。问答结果沿用现有的 probe 表。results.json 增加 `replay` 段：设置、各组各剧本用量与费用、是否完整、停止原因。

## 4. 费用与安全

- `--dry-run --replay` 估算整个重放的请求数、token 与费用（低：可缓存部分全部命中；高：全部按未缓存 / 缓存写计价，含超过 100K 的价档），不发任何请求。
- 必须给 `--max-cost`；费用守卫覆盖重放请求与问题请求。即将超出时停止**所有**真模型请求，剧本照常跑完；报告标出未完成的组与剧本，未完成的组不参加对照表。
- 单个请求失败（例如过长被拒的 400/422、拒答、格式错误）：记为该请求的错误并计入已报告的用量，**不**停止重放；连续 3 次 400/422 的停止规则只适用于问题请求。401/402/403/404 与网络重试用尽仍停止所有真模型请求。
- 密钥规则与问答评测相同：只从环境读取，不出现在任何输出与错误信息中。
- 估算参考（用户 DeepSeek 价目：未命中 $0.15、命中 $0.003、输出 $0.6 / 百万 token）：长档两个剧本 A、C、D、E 共约 950 万输入 token，按估算的命中率约 $0.1（全不命中约 $1.5）；超长档 C、D、E 共约 1.4 亿输入 token，约 $0.8（全不命中约 $21）。问答评测里真实命中低于估算（C 组 69%），所以建议超长档 `--max-cost 8`（相当于约 75% 命中）。

## 5. 局限（写入报告说明）

- 各组共用开头一小段固定模板（几百 token），后运行的组可能多命中一点缓存，影响很小。
- 真模型回答不改变项目：衡量费用、缓存与问答，不衡量工作成果的质量。
- 服务商的缓存是尽力而为（DeepSeek 不保证命中），其波动算作真实结果的一部分；只跑一次。
- 重放请求的输出被截断为 16 token，真实费用中的输出部分偏低；输入部分是本评测的重点。

## 6. 测试

- 离线、可注入模型：每个请求（剧本与额外）都按顺序发给重放模型，段内容与 `CallRecord` 记录的一致；剧本走向不受回答影响。
- 不加 `--replay` 时逐字节相同；加 `--replay` 时 `CallRecord` 与不加时相同。
- 费用守卫在重放中途停止、报告标出未完成；单个 400 不停止重放；`--dry-run --replay` 不调用 `fetch`。
- 交付前用本地假 DeepSeek 服务做一次端到端运行。
