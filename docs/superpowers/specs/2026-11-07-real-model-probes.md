# 真模型评测：关键信息问答（probe）

- 日期：2026-11-07
- 状态：已实现并运行（2026-11-07，用户本地用 DeepSeek 运行）
- 上游：`2026-10-31-bench-design.md`（假模型评测）、`2026-11-06-core-stream-mode.md`（长项目模式结果）

## 1. 目标

假模型只能衡量"关键信息是否出现在上下文里"。本评测回答下一个问题：

> 在同一时刻、各组各自给 Bot 的上下文里，真模型能否**答对**这个 Bot 需要知道的关键事实？尤其是改需求之后会不会还按旧需求回答？

同时用服务商返回的真实用量（输入、缓存读、缓存写）核对评测里的缓存假设（R-B19）。

## 2. 方法

- **剧本照常由脚本驱动**（各组的请求序列与现在完全相同），真模型**只回答插入的问题**，不改变剧本走向。这样各组面对的是同一个项目进程，差别只来自上下文。
- **问题（probe）随事实标注：** 事实新增可选字段 `probe: { question; expect: string[]; reject?: string[] }`。
  - `expect`：答案中必须出现其中至少一个（不区分大小写）的字符串，例如 `"12x12"`、`"eu-central-1"`。
  - `reject`：出现即判错的旧答案，例如改需求前的旧值（用于检测"按旧需求回答"）。
- **何时提问：** 对每个带 probe 的事实，在它的受众 Bot 的剧本请求中按固定规则取样（第一次机会、中间一次、最后一次；可配置），在该请求的上下文末尾附上问题，单独发一次请求给真模型。
- **判分：** 答案含 `expect` 之一且不含任何 `reject` → 对；含 `reject` → "旧答案"；其余 → 错。不使用模型评分。
- **参与组：** 默认 A（参照）、C（默认：自动长项目模式）、D、E；B、F 可选（费用高）。
- **剧本：** 默认长档两个剧本；标准档可选；超长档只抽样部分事实（命令行限制每个剧本最多问题数）。

## 3. 模型与费用

- 模型适配器接口沿用 `Model`，新增真模型适配器：默认 Anthropic Messages API（`claude-haiku-5-5`，支持提示缓存，按段的可缓存标记设置缓存断点），可配置模型名；预留其他服务商的适配器位置。
- 密钥通过环境凭据注入，不写入仓库。
- **OpenAI 兼容服务（2026-11-07 增补）：** 用户选择在本地电脑用 DeepSeek API 运行。新增 OpenAI 兼容适配器（`--provider openai --base-url … --model …`），价目由用户用 `--price` 给出（不内置第三方价目）；这类服务自动做前缀缓存，缓存写记为 0。
- **费用控制：** `--dry-run` 只统计将要发送的问题数与 token 数并按价目估算费用；正式运行需要 `--max-cost <美元>`，超过即停止并保存已有结果。
- 报告同时给出：各组各类事实的答对率、"旧答案"率、真实用量（输入 / 缓存读 / 缓存写）与按价目计算的真实费用，以及与 R-B19 估算的对照。
- 结果确定性：真模型输出不确定，报告给出温度设置与运行次数；同一问题默认问一次，可选重复取多数。

## 4. 不做

- 让真模型驱动剧本（Bot 自己决定做什么）——留到之后，成本和不确定性都高得多。
- 模型评分（LLM 当裁判）。

## 5. 结果

用户在本地电脑用 DeepSeek（OpenAI 兼容接口，模型 `deepseek-flash`，`thinking` 关闭，`temperature` 0，`max_tokens` 200）运行；C 组用长项目模式 `auto`（75）；每个事实取第一次 / 中间 / 最后一次机会（`fml`），每题问一次（§3 的"重复取多数"未实现）。价目由用户给出：输入未命中 $0.15、命中 $0.003、输出 $0.6（每百万 token）。原始报告：`docs/superpowers/runs/probes-long-report.md`、`docs/superpowers/runs/probes-xlong-report.md`。超长档没有按原计划只抽 C、D、E 各 45 题，而是 A、C、D、E 都问了全部 135 题；两档合计花费 $0.53，没有错误、没有触发费用上限。

### 5.1 答对率

| 组 | 长档（2 个剧本，每组 132 题） | 旧答案 | 超长档（每组 135 题） | 旧答案 |
|---|---:|---:|---:|---:|
| A 单 Agent 全历史 | 100.0% | 0.0% | 97.8% | 1.5% |
| **C 本项目（auto）** | **97.7%** | **0.8%** | **97.0%** | **2.2%** |
| D 共享日志 | 97.0% | 1.5% | 97.0% | 1.5% |
| E 轮流群聊 | 98.5% | 0.0% | 95.6% | 2.2% |
| 无上下文对照 | 18.2%（44 题） | — | 35.6%（45 题） | — |

- 四组都在 95% 以上，彼此最多差 4 题（长档 A 132、D 128；C 与每组差 0–3 题；每组 132–135 题、只跑一次），**不能据此排出 A、C、D、E 的高下**；能说的是：C 的小上下文没有让真模型答得更差。
- 无上下文对照只答对 18% / 36%，说明这些问题大多必须靠项目上下文回答；约定类（行业惯例，如 ISO 8601、游标分页）最容易猜中（30% / 60%）。
- 超长档上改需求类是所有组最弱的一类（85–91%）；长档上则不是（C、D 的失败类更低，E 的改需求类为 100%）。旧答案全部出在改需求类；各组旧答案率都不超过 2.2%。
- 与假模型的"事实可见率"一致：C 在长档可见率 96.9%、答对 97.7%；超长档 99.1%、答对 97.0%。

### 5.2 同样的答对率，发送的上下文差多少

问题请求就是该组在那一刻的完整上下文加一个问题，所以下表的真实 prompt token（服务商计数）直接反映各组上下文大小：

| 组 | 长档 prompt token | 长档费用 | 超长档 prompt token | 超长档费用 |
|---|---:|---:|---:|---:|
| A | 2,409,696 | $0.0201 | 17,421,292 | $0.0842 |
| **C** | **618,074** | **$0.0249** | **1,637,258** | **$0.0832** |
| D | 1,022,267 | $0.0280 | 9,174,292 | $0.1385 |
| E | 928,219 | $0.0264 | 7,280,089 | $0.1215 |

- 超长档上 C 以与 D 相同的答对率，发送的 token 约为 D 的 1/5.6、E 的 1/4.4；费用比 D 低 40%、比 E 低 32%。长档上 C 的 token 约为 D、E 的 60–67%，费用低 6–11%。A 的单一历史几乎全部命中缓存，超长档费用与 C 相当（$0.0842 对 $0.0832），长档最便宜（$0.0201）。
- 这里的费用是**问题请求**的费用，不是整个项目的费用；整个项目的费用仍以 R-B19 估算为准（README 长项目模式表）。

### 5.3 缓存假设（R-B19）对照

| 组 | 长档：估算可缓存 % | 真实缓存命中 % | 超长档：估算可缓存 % | 真实缓存命中 % |
|---|---:|---:|---:|---:|
| A | 98.8 | 97.0 | 99.8 | 98.8 |
| C | 90.2 | 77.6 | 94.9 | 68.8 |
| D | 93.0 | 84.7 | 99.3 | 91.9 |
| E | 92.7 | 84.1 | 99.2 | 90.9 |

- 真实命中都低于估算，C 低得最多。原因之一是问题请求不是剧本请求序列：每个 Bot 只在取样的几个时刻被问，彼此相隔很远，服务商缓存里只有更早的问题请求留下的前缀，而 R-B19 估算的是"与该 Bot 上一次请求相同的前缀"。C 的流每 8,000 token 重新做一次快照，相隔很远的两次问题请求之间往往隔着快照，所以前缀复用最少；A、D、E 的历史只追加，相隔再远前缀也相同。
- 因此这组数据**不能**直接验证剧本运行中的缓存命中率；它说明的是：请求稀疏时（例如 Bot 很久才被唤醒一次），C 的缓存优势会比 R-B19 估算的小。要验证剧本运行本身的缓存，需要让真模型按剧本顺序接收每一个请求（成本高得多，未做）。

### 5.4 局限

- 只跑一次、一个模型（DeepSeek `deepseek-flash`），温度 0；组间差异最多 4 题，属于噪声范围。
- 判分只用字符串规则；无上下文对照给出了"猜中"的下限，但个别宽泛的期望答案仍可能多给分（已列入 Task 3 的遗留项）。
- 真模型只回答插入的问题，不驱动剧本；Bot 是否会在真实工作中用上这些信息，仍未衡量。
- 价目由用户提供，费用只与这些价目一样准确。

## 6. 实施中的裁定

- **R-Q1：** 付费运行前必须先 `--dry-run` 估算并取得用户同意；密钥只从环境读取。
- **R-Q2：** §3 的"重复取多数"未实现，每题问一次，结果中写明。
- **R-Q3：** `expect` 写事实内容中的具体值，不写合成标记；至少一个 `expect` 出现在引入该事实的那一步文本中，其余可为具体的同义写法。
- **R-Q4：** 改需求类问题以 "Give only the current value." 结尾，旧值放进 `reject`；`reject` 不得出现在该事实之后任何一步的文本中。
- **R-Q5：** 判分归一化把 `-`、`_`、`/` 视为空格（答案与期望两侧）。
- **R-Q6：** 加入无上下文对照（组 `none`），默认开启，`--no-probe-control` 关闭。
- **R-Q7：** 用户改为在本地用 DeepSeek 运行：新增 OpenAI 兼容适配器，价目由用户用 `--price` 给出，不内置第三方价目。
- **R-Q8：** 网络重试用尽、或连续 3 次 400/422 时停止全部提问（已有结果保留）；`thinking: {type: "disabled"}` 默认发送（DeepSeek 默认开启思考），可用 `--thinking omit` 关闭（用户提交 b4957be 加入，最终评审后改为可选）。
