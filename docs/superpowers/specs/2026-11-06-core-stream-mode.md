# 核心库：长项目模式（只追加的每 Bot 简报流）

- 日期：2026-11-06
- 状态：已实现
- 上游：`2026-11-05-stream-brief-estimate.md`（原型与估算）、`2026-10-11-group-context-layer-design.md`（第 5、6 节）

## 1. 背景与决定

估算结论（公平核算，含 Bot 自身输出）：只追加的简报流在超长项目上费用约为 D/E 的 1/4、单次上下文约 1/10，可见率 93–96%；长项目与 D/E 持平；短项目贵约 50%。

决定（2026-11-06，按负责人判断执行）：
1. 把简报流做进核心库，定位为**长项目模式**：可选开启，或按项目历史长度自动开启；短项目沿用现有简报。
2. **撤下的契约保留可见**：重新拆分撤下的契约进入项目板的"已撤下契约"记录，长项目模式的快照与追加中带上它们（紧凑形式，含规格原文）。理由：剧本的事实定义与 D/E 的行为都认为它们仍需被知道；工作块结束后，后续工作仍依赖当时的接口约定。
3. 用真模型衡量质量放到下一阶段。

## 2. 核心库

### 2.1 选项

- `createProject({ …, stream?: { mode?: 'off' | 'on' | 'auto'; restreamTokens?: number; autoAfterEntries?: number } })`
  - 缺省 `mode: 'off'`：所有现有行为与输出逐字节不变。
  - `on`：所有 Bot 使用流。
  - `auto`：每次 `buildStream` 用当前账本条目数（最新 seq）与 `autoAfterEntries` 比较：不足时与 `off` 完全相同（输出相同、不写流状态、`recordOwnOutput` 无操作）；达到的那次请求对该 Bot 是快照，之后为追加。切换单向、按项目持久化（存储里的 `streamAutoOn`）：开启后即使重新打开项目并调大阈值也不再关闭。每个 Bot 的第一次流式请求各自是快照。`autoAfterEntries` 缺省 75（由第 5.3 节的评测决定）。
  - `restreamTokens` 缺省 8,000。
  - `snapshotHumanKeep` 缺省 40，可为 0（快照折叠全部人类消息）。

### 2.2 接口

- `project.buildStream(botId, { maxTokens, trigger, request?: { kind: 'brief' } | { kind: 'review'; deliverableId } | { kind: 'planning' } })` → `StreamBundle`：返回该 Bot 本次请求的完整段列表（前缀 + 本次追加，或新快照），所有段标记可缓存；`stats` 覆盖全部段；`snapshot` 表示本次是否为新快照。`StreamBundle` 是 `ContextBundle` 的兼容超集：段类型为 `StreamSegmentKind = SegmentKind | 'updates' | 'own'`（`updates` 为全项目信息变更，`own` 为 `recordOwnOutput` 的文字）；`SegmentKind` 本身不变，因此现有简报输出不变（裁定 R-M1；以 `ContextBundle` 为类型的宿主需要一次类型转换）。关闭时返回现有方法的 `ContextBundle` 原样（无 `snapshot`）。行为与现有方法一致：叫醒、已看过确认、审查与拆分上下文的状态变化不变。
- `project.recordOwnOutput(botId, text)`：宿主把该 Bot 本次的回复与工具调用文字交给核心库，追加到流里（计入重新快照预算）。不调用时流里不含 Bot 自身输出。
- 关闭时这两个方法仍可调用：`buildStream` 退化为现有的 `buildBrief` / 审查 / 拆分上下文，`recordOwnOutput` 不做任何事。

### 2.3 流的内容（结构化，不解析文字）

- **快照：** 公共说明、记忆、工作区、项目板（含全项目信息全文与"已撤下契约"）、投影；以及截至快照的全部人类消息——人类消息超过 `snapshotHumanKeep`（缺省 40）条时，更早的折叠为一段"较早的指示"摘要行列表（每条只保留前 160 个字符）。
- **追加：** ①全项目信息变更：按 id + 版本的项目板变更事件（新增、改版、撤下——撤下的契约以紧凑形式进入"已撤下契约"并追加一次）与新的人类消息；②公共说明（团队名单）变化时整段重新追加（裁定 R-M2，补上原型名单冻结的缺口）；③该 Bot 的记忆、笔记、投影的条目级变化（见下）；④核心库增量中与该 Bot 相关的条目（去掉流已携带的人类消息；快照时被折叠为 160 字符的人类消息仍完整保留在增量中）；⑤触发说明；⑥`recordOwnOutput` 的文字。
- **条目级变化：** 输入为结构化条目，不解析渲染文字——投影按拥有的工作块分块（工作块字段：状态行、Brief、依赖、写入范围、审查轮数；契约、决定、事实、失败、上游交付、重叠），记忆（Persona、Skills、置顶、摘要、最近）与笔记（置顶、摘要、最近）。单个条目用核心库的渲染函数渲染，文字与简报一致。追加段为 `<标题> — updates`，按工作块再按小节归组：工作块字段在 `(part <工作块>)` 下，其他条目在 `<小节标题> (part <工作块>)` 下（记忆与笔记无工作块）。
  - 新条目按简报当前的形式追加（已读的为 `(seen)` 形式）；内容变化的条目追加完整新文字（多行条目整条追加）；新的上游交付只追加新的一行。
  - 删除：置顶笔记、列表条目（契约、决定、事实、失败、上游交付、重叠、技能）与工作块字段被删除时追加一行 `no longer: …`（带 id 的条目只取首行）；不再拥有的工作块只追加一行 `no longer: <工作块行>`。摘要与 Persona 只在变化时整段追加。
  - 不算变化：已读压缩（同一条目变为 `(seen)` 形式）、条目重排、笔记或记忆滚出"最近"窗口、预算裁剪使简报少显示的条目——这些既不追加 `no longer`，重新出现时也不重复追加（"最近"窗口按序列对齐：窗口开头与已显示序列末尾相同的部分为旧条目，其后为新条目，因此再次写入的相同笔记仍算新条目；对不齐时按多重集合比较）。
  - 相同条目按多重集合计数：同一小节两个相同条目是两个条目，不同工作块中的相同条目互不影响。
- **重新快照：** 快照后追加超过 `restreamTokens` 时，下一次请求发新快照。
- 流状态（已显示的条目与版本、人类消息序号、各小节条目、上次的段列表）按 Bot 持久化在存储中（项目元数据键 `stream:<botId>`，带版本号；版本不符时下次请求为快照）；内存与 SQLite 两种存储行为一致。请求先读取流状态与人类消息，再生成简报，读取失败不留下副作用。

### 2.4 项目板

- `ProjectBoard.retiredContracts?: Contract[]`：批准的新计划不再包含某契约时，该契约（最后版本）进入此列表；读取旧数据时缺省为空。现有简报与公共项目板渲染不显示它（关闭流时输出不变）。

## 3. 评测

- C 组新增 `--c-stream core`：使用核心库的 `buildStream` 与 `recordOwnOutput`（宿主按 E 的作者格式提供自身输出）；保留原型 `on` 以便对照。
- 核对：`core` 与原型 `on` + 自身输出在同一预算下费用与可见率接近（差异原因写明）；其他组不变；输出确定。
- 选择 `autoAfterEntries`：在三档剧本上运行 `auto` 的若干阈值，取"短剧本不开启、长与超长剧本开启"的阈值，写入文档与 README。

## 4. 不做

- 真模型评测。
- 改变叫醒规则。
- 让宿主改用流以外的方式记录自身输出。

## 5. 结果

运行方式（评测已构建；输出到仓库外的目录）：

- `pnpm -C packages/bench bench run --scenario all --group all --out <目录> --stamp <名>`，分别加 `--c-stream off`（D、E 与 C 关闭时的数字）、`--c-stream on --c-stream-own on`（原型 + 自身输出，8k）、`--c-stream core`（核心库的流，8k）；`core` 运行两次。
- `--scenario all --group C --c-stream auto --auto-after <n>`，n = 50、60、75、100、150、200、300、400；`75` 运行两次；另以不带 `--auto-after`（核心库缺省值 75）运行全部六组一次。

核对结果：

- `off`、`on`、`on --c-stream-own on` 三种设置在本次改动前后（`git stash` 构建对比）的 `results.json` 与 `report.md` 逐字节相同，参数行也不变；
- `core` 两次、`auto 75` 两次的 `results.json` 与 `report.md` 各自逐字节相同（`cmp`）；不带 `--auto-after` 的运行与 `--auto-after 75` 的 C 组 `metrics`、`records` 相同；
- `core` 下 A、B、D、E、F 的 `metrics` 与 `records` 与 `off` 相同（测试 `cli.test.ts` 也在 product-plan 上核对）；C 组每个剧本核心错误均为 0、全部收尾；请求的数量、Bot、步与 `off` 相同；
- `auto` 在未达到阈值的剧本上 C 组输出与 `off` 完全相同（含上限行）；
- 一次全部剧本、全部组的运行约 15 秒（不含构建）。

快照次数来自报告新增的每剧本一行 `Group C stream: used from step N; S snapshots; ledger L entries.`（C 组 `metrics.stream`）；"重新快照"为快照次数减去使用流的 Bot 数。

差异与原因（按段类型汇总的 token 来自 `results.json` 中 C 组请求记录的分段；已撤下契约的数量来自在仓库外用已构建的评测重放 C 组、运行结束后读 `board().retiredContracts` 的临时脚本，未提交）：

- **两者的重新快照次数在三档都相同**（0 / 14 / 61），费用差别不来自快照频率，而来自快照与追加的内容。
- **撤下的契约保留可见**（决定 2，超长档的主要差别）：超长档运行结束时项目板上有 46 条已撤下的契约（JSON 约 13.8k 字符，约 3.5k token），核心库的每次快照都带上它们，撤下时追加一行而不是让旧文字在下次快照时消失。因此 contract 可见率 74.4% → 99.2%，总可见率 94.6% → 99.8%（原型在估算文档第 5.3 节中的"项目板条目被重新拆分撤下"一类漏看在核心库中基本消失）；代价是项目板段的输入 token 从 353 万增至 511 万（未缓存部分 22.6 万 → 32.5 万），全项目更新段的未缓存部分 8.5 万 → 10.6 万，超长档费用 +14.8%（仍比 D 便宜 72.8%、比 E 便宜 70.0%），中位数与最大值约增 17% / 15%。长档只有 long-event 的 2 条撤下契约，contract 98.8% → 99.2%；标准档的 product-plan 有 1 条，可见率不变。
- **团队名单的追加**：原型在两次快照之间冻结公共段（团队名单），核心库在名单变化（重新拆分加入成员）时追加。标准档 C 的 common 段输入 14.4k → 24.1k、未缓存 0 → 1.6k，是标准档 +3.1% 费用（61,557 → 63,441）的主要来源；长档、超长档中这一项很小。
- **条目级更新与已读压缩去重**：原型按渲染文字逐行比较记忆、笔记与投影，核心库按条目比较、不把已读压缩当成变化，并且同一次追加中已在全项目更新里出现的条目只给"（seen）"短形式。长档的投影段输入 48.9 万 → 42.2 万（−14%）、超长档 151 万 → 143 万（−5%）。长档其余各段（更新、自身输出、触发）的总量略有增减，来自快照落在不同的请求上（快照前追加的内容不同），合计使长档费用只差 +0.4%（370,385 → 371,766）。
- **折叠较早的人类消息**：本次剧本的人类消息最多 37 条（超长档），少于 `snapshotHumanKeep`（40），因此没有发生折叠，对结果没有影响；更长的项目上快照会因此变小。
- **剩余的漏看**：标准档 3 次是 flappy-bird 中 web 从未收到的 `contract-hitbox-12x12`（Bot 聊天约定，与原型相同）；长档 2 次、超长档 26 次未逐次复核。按估算文档第 5.3 节的分类，原型带自身输出时超长档有 24 次"从未送达"（qa 不在相关范围内的 Bot 聊天）与 4 次 Bot 自己的消息，核心库的 26 次应主要属于这两类。

### 5.2 `core` 与 D、E

- 标准档：可见率与 D、E 相同（95.7%），费用高约 55%–59%；单次请求最大 7.7k，高于 D、E 的约 3k。即短项目不该用流，这是 `auto` 的理由。
- 长档：可见率 99.9%，高于 D（98.1%）、E（97.7%）；费用比 D 低 1.8%，比 E 高 2.8%。
- 超长档：可见率 99.8%（D 100%、E 99.2%），费用比 D 低 72.8%、比 E 低 70.0%；单次请求中位数约 9.8k、最大约 18.7k，约为 D、E 的 1/5。

### 5.3 选择 `autoAfterEntries`

选择 **75**，理由：

- **长档、超长档开启得足够早**：75 在长档第 60–61 步（共 160–164 步，约三分之一处）开启，超长档在第 123 步（共 1,154 步）。长档费用比 D、E 都低（−6.2% / −1.8%），可见率 96.9%，取得从 `off` 到 `core` 可见率提升的约 85%；超长档 99.1%，约为提升的 98%，费用与 `core` 相差 1.5%。
- **再往上很快变差**：100 时长档可见率降到 93.4%、比 E 贵；150 以上长档基本回到 `off`；400（原暂定值）在长档完全不开启，超长档要到第 647 步才开启（88.4%）。
- 长档上 `auto` 比从头开启的 `core` 便宜（355k 对 372k）：项目早期的普通简报比流的快照更小，流的收益在项目变长后才出现；代价是开启前那一段的可见率与 `off` 相同（这一段的漏看使长档可见率 96.9% 低于 `core` 的 99.9%）。

### 5.5 注意事项

- 结果来自脚本化的假模型，只衡量上下文大小与标记的字面可见，不衡量 Bot 是否用上了信息、输出质量与一致性。
- 流中带 Bot 自身的输出：评测按 E 的作者格式（回复、带参数的工具行、交付全文）调用 `recordOwnOutput`。宿主若不调用，费用更低但流里没有 Bot 自己说过的话（原型的估算见估算文档第 5.1 节）；若用更长的格式（例如带工具结果），费用更高。
- 撤下的契约保留可见：可见率按剧本的事实定义计算；若认为撤下的契约不应再被看到，这部分快照内容就是多余的费用（超长档上核心库比原型贵 14.8%，主要来自这一项，见第 5.1 节）。
- 真实的缓存过期没有建模：R-B19 只按与上一次请求相同的最长前缀计算；空闲超过供应商缓存寿命的 Bot 下一次请求实际上要全部重新计费，单次请求可设的缓存断点数与首次写入缓存的额外费用也没有建模。流越长、Bot 越空闲，对流越不利。
- 阈值的单位是账本条目：评测中 C 组只把人类消息、工具调用与核心库事件写入账本，脚本里 Bot 的回复不入账；把每条 Bot 回复都当作聊天写入账本的宿主，账本增长更快，75 会更早到达，短项目也可能开启。这样的宿主可以调大 `autoAfterEntries`。在这些剧本上，即使把脚本里每条 Bot 回复都当作聊天记入账本，标准档结束时也只有约 65 条，仍略低于 75（近似值；额外请求的回复会再增加一些）。
- 与 `publicBoard` 合用：开启流时设 `publicBoard: { contracts: true, failures: true }`，投影不再重复契约与失败，可见率不变，费用约低 2%–5%（核心库从头开启：63,441 / 371,766 / 2,025,560 → 61,102 / 353,213 / 1,982,358，标准 / 长 / 超长档；`--c-stream core --c-public all` 复测）。后续可让流自己去掉投影中的这两段，不必依赖开关。
- 选择只基于本仓库的六个剧本（三个标准、两个长、一个超长），长档与标准档之间没有中间长度的剧本。
- 超长档上 A、B 的单次请求超过 128,000 token 的窗口（本节只与 D、E 比较）；E 在超长档压缩一次，压缩摘要假定保留全部标记（对 E 有利）。
