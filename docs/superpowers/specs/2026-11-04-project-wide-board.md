# 核心库：项目级信息上公共项目板（可开关）

- 日期：2026-11-04
- 状态：已实现
- 上游：`2026-11-02-core-visibility-gaps.md` 第 5 节、`2026-11-04-context-segment-alignment.md` 第 5 节、`2026-10-11-group-context-layer-design.md` 第 5.2 节

## 1. 背景与目标

C 组在长剧本上费用最低（321k，E 362k，D 379k），但关键信息可见率只有约 67%（标准剧本 37%），其他多 Bot 组 90–100%。逐条分析表明漏看的原因是三种设计取舍：按相关性裁剪投影、看过就折叠、聊天消息只显示一次。约定已经在公共项目板上，所有 Bot 每次都能看到，C 组约定类事实可见率 100%。

本设计把另外三类项目级信息也放上公共项目板，每类一个开关；评测分别在开与关两种设置下运行，给出费用与可见率的对照，再决定默认值。

目标：
- 三个机制各自可开关，默认全部关闭（行为与现在完全相同）。
- 评测给出"全关 / 各开一项 / 全开"五种设置下 C 组的费用与可见率，其他组不变。
- 全开时长剧本可见率目标 ≥ 90%；费用如实报告，不设上限。

## 2. 三个机制

在 `createProject` 选项中新增 `publicBoard?: { directives?: boolean; contracts?: boolean; failures?: boolean }`，缺省全为 `false`。

### 2.1 指示（directives）

- 人发的每条聊天消息（`author.kind === 'human'`）原文进入公共项目板新的"## Directives"一节，按时间顺序，格式 `- [#seq 姓名] 原文`。
- 只保留最近 `directivesKeep` 条（新选项，默认 20），更早的省略并显示 `(N earlier directives omitted)`；不做模型摘要。
- 开启后，人发的聊天消息不再出现在任何 Bot 的增量段（已在项目板上，避免重复）；叫醒规则不变。
- 规划上下文中的"全部人类消息"保持不变（规划需要完整历史）。

### 2.2 契约（contracts）

- 公共项目板新增"## Contracts"一节，列出全部契约：`- [id@版本] 来源 → 去向: 规格原文`。
- 开启后，投影与审查上下文不再重复契约原文（只在项目板上出现一次）。

### 2.3 失败记录（failures）

- 公共项目板新增"## Failures"一节，用与投影相同的字段布局（尝试 / 失败原因 / 影响）。
- 开启后，投影与审查上下文不再重复失败记录。

### 2.4 共同规则

- 新增各节在项目板中的顺序：Goal、Constraints、Directives、Conventions、Contracts、Failures、Workstreams；未开启的节不出现。
- 项目板段仍为第 4 段、可缓存；任何一节变化都会使该段及其后的缓存失效——这是本设计的主要成本，需在评测中如实体现。
- "已看过"规则只作用于投影；项目板上的内容不折叠。
- 审查、规划上下文与简报共用同一个项目板段文字（保持第 1–4 段逐字节相同）。

## 3. 评测

- 命令行新增 `--c-public none|all|directives,contracts,failures`（逗号分隔子集），缺省 `none`；参数写入报告与 `results.json`。
- 分别以 `none`、`directives`、`contracts`、`failures`、`all` 运行五个剧本六组，汇总一张 C 组对照表（每种设置的费用、可见率、按事实类别的可见率）；其他组每次结果应完全相同。
- 结果写入本文档第 6 节；不为 C 组修改剧本、标注或其他组。

## 4. 风险

- 项目板变长、变化更频繁：所有 Bot 的项目板段缓存更常失效，费用可能明显上升。
- 指示节包含所有人类消息，包括寒暄与提问，会带入噪声；`directivesKeep` 限制其增长。
- Bot 之间只在聊天中约定、没有写成契约的内容，本设计不覆盖（需要 Bot 调用契约工具或抽取模型）。

## 5. 不做

- 模型摘要或抽取。
- 改变叫醒规则或增量的其他规则。
- 改变默认值（待评测结果后另行决定）。

## 6. 结果

运行方式：对 `none`、`directives`、`contracts`、`failures`、`all` 各运行一次 `pnpm -C packages/bench bench run --scenario all --group all --c-public <设置> --out <目录> --stamp T`（五个剧本、六组）。核对结果：

- A、B、D、E、F 在五种设置下的汇总行、各剧本指标与全部请求记录完全相同；
- C 组在每种设置、每个剧本中核心错误均为 0，全部收尾；
- `all` 运行两次，`results.json` 与 `report.md` 逐字节相同。

### 6.1 对照表

费用为成本单位（`--cache-ratio 0.1`），同一档剧本相加；可见率为同一档剧本合并计算（命中 / 机会）。按类别的可见率按事实 id 前缀（`change-`、`conv-`、`contract-`、`fail-`）合并。

| 设置 | C 费用 标准 | C 费用 长 | C 可见率 标准 | C 可见率 长 | change 标准 / 长 | conv 标准 / 长 | contract 标准 / 长 | fail 标准 / 长 |
|---|---|---|---|---|---|---|---|---|
| none | 47,291 | 321,191 | 37.1%（26/70） | 66.9%（1087/1626） | 9.1% / 56.7% | 100% / 100% | 50.0% / 26.6% | 30.0% / 19.0% |
| directives | 55,852 | 400,723 | 80.0%（56/70） | 79.9%（1299/1626） | 100% / 100% | 100% / 100% | 50.0% / 26.6% | 30.0% / 19.0% |
| contracts | 50,890 | 377,185 | 41.4%（29/70） | 75.0%（1219/1626） | 9.1% / 58.6% | 100% / 100% | 71.4% / 76.2% | 30.0% / 19.0% |
| failures | 48,293 | 357,301 | 45.7%（32/70） | 75.8%（1232/1626） | 9.1% / 56.7% | 100% / 100% | 50.0% / 26.6% | 90.0% / 100% |
| all | 61,565 | 505,299 | 92.9%（65/70） | 96.4%（1567/1626） | 100% / 100% | 100% / 100% | 71.4% / 76.2% | 90.0% / 100% |

各类别机会数：标准档 change 33、conv 13、contract 14、fail 10；长档 change 490、conv 709、contract 248、fail 179。

参照（与设置无关，五次运行相同）：D 组费用 标准 40,024、长 378,684；E 组费用 标准 40,820、长 361,692。D、E 可见率 标准 95.7%，长 98.1%（D）/ 97.7%（E）。

相对 `none`，C 组长档费用：`directives` +24.8%，`contracts` +17.4%，`failures` +11.2%，`all` +57.3%。`all` 下长档费用比 D 高约 33%，比 E 高约 40%；标准档 `none` 已高于 D、E，`all` 再高约 30%。

每个开关只改变自己那一类的可见率（`contracts` 使长档 change 由 56.7% 升到 58.6%，是因为契约规格按标注规则 R-L11 也带着变更的标记）。`directives` 下没有因 `directivesKeep`（20 条）截断而漏看的变更：两档 change 均为 100%。

### 6.2 `all` 下仍然漏看的事实

标准档 5 次、长档 59 次漏看，全部来自四条事实：

| 剧本 | 事实 | 机会 / 命中 | 原因 |
|---|---|---|---|
| flappy-bird | `contract-hitbox-12x12` | 8 / 4 | Bot 之间在聊天中约定，未调用契约工具，项目板上没有这条契约。coder 写进了自己的置顶笔记，每次都看到；artist 只在一次增量中看到；web 从未收到（消息只发给 artist）。 |
| event-plan | `fail-venue-price-excl-vat` | 2 / 1 | 只写在审查意见中，没有记录为失败条目，所以不进入"## Failures"；venue 在下一次请求中看到一次审查结果，之后不再出现。 |
| long-app | `contract-error-envelope` | 26 / 2 | Bot 之间的聊天约定（backend 发给 web、mobile），未写成契约；两者各看到一次，之后漏看。 |
| long-event | `contract-badge-csv` | 38 / 3 | 同上（venue 与 marketing 之间的聊天约定）；venue 只在 marketing 后来的一条聊天消息和一次交付带出标记时又看到两次。 |

即：剩下的漏看都属于第 4 节已列出的风险——只在聊天（或审查意见）中出现、没有成为项目板条目的内容。三个开关只把已经是项目板条目（契约、失败记录）或人类消息的内容放上公共项目板；Bot 之间的聊天约定仍然只显示一次。覆盖它们需要 Bot 调用契约工具或抽取模型（第 5 节不做）。

### 6.3 费用来源

费用上升主要来自项目板段的缓存失效，而不是内容本身：

- 长档 C 组项目板段的 token 总量由 `none` 的约 18.8 万增至 `all` 的约 46.7 万，其中可缓存比例由 40% 降到 32%：每条人类消息、新契约或新失败记录都改变项目板段，使所有 Bot 下一次请求中该段及其后各段的缓存失效。投影段相应缩短（约 14.9 万 → 12.4 万），增量段因不含人类消息略缩短。
- 报告中的上限行（假设服务商缓存核心标记为稳定的各段，不论位置）在五种设置下几乎不变：长档 `none` 213,068、`all` 212,627；标准档 34,156 → 31,544。也就是说，若缓存不要求前缀连续，`all` 的额外费用基本消失；在当前"最长相同前缀"规则下则如实体现为 +57%。

本节不给出默认值建议，由用户根据上述对照决定。
