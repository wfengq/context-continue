# 评测补充：长剧本与上下文分段重排

- 日期：2026-10-31
- 状态：待审阅
- 上游：`2026-10-31-bench-design.md`（评测设计）、`2026-10-11-group-context-layer-design.md` 第 5.2 节（简报分段）

## 1. 背景

第一版评测（三个 20–40 步的剧本，六组统一缓存规则）的结果：C 组估算费用 37.5k，D 组 24.7k，E 组 26.3k。分析：

- C 组的项目板段排在前面，约一半的请求中项目板有变化，导致其后的段都无法命中缓存。
- 剧本很短（最大单次请求约 2.8k token），C 组"上下文规模不随项目变长而增长"的特点体现不出来，E 组压缩一次都没有触发。

本补充回答：**项目变长后，C 组是否追上或超过其他组。** 先做低成本的分段重排，再加长剧本；之后再决定是否做"项目板只追加"的较大改动。

## 2. 核心库：简报分段重排

- 新顺序：`common`、`memory`、`workspace`、`board`、`projection`、`delta`、`trigger`。
- 可缓存标记：`common`、`memory`、`workspace`、`board` 为 true，其余 false。
- 理由：私有记忆与工作区很少变化（第一版数据中 96 次请求分别变化 0 次与 3 次），项目板约一半请求有变化，放在稳定段之后。
- 预算裁剪的优先次序不变（按段的种类，不按位置）。
- 更新设计文档第 5.2 节与相关测试。

## 3. 长剧本

- 新增两个长剧本，各 150–300 步：
  - `long-app`：一个应用从需求到上线，8 个 Bot、约 10 个工作块；
  - `long-event`：一次大型活动筹备，6 个 Bot、约 8 个工作块。
- 每个长剧本必须覆盖：至少 3 次重新拆分、至少 4 次人中途改需求、至少 6 次审查未通过、至少 8 条新增约定、至少 10 次 Bot 之间询问；交付物有多个版本，后续版本更长。
- 剧本用确定性的生成脚本 `packages/bench/src/gen/` 产生（放在 `src/` 下才能随 `tsconfig.build.json` 编译；`pnpm -C packages/bench gen:scenarios` 重新生成）（不使用随机数；或使用固定种子），生成结果 JSON 提交到仓库；测试断言"重新生成 = 已提交文件"。
- 交付物与回复用模板拼出的英文文本，长度规则同第一版（交付物 300–1500 字符，后续版本可到 3000 字符）。
- 校验：第一版的 20–40 步限制只适用于标准剧本；长剧本标记 `tier: 'long'`，适用 150–300 步。
- 剧本必须遵守第一版的全部规则（核心库工具参数形状、负责人是员工、审查前已有交付物、C 组无核心错误且项目收尾）。

## 4. 报告

- 标准剧本与长剧本分别汇总，不混在一张汇总表里。
- 新增"随步骤增长"的数据：每组每 25 步的平均单次请求长度（文字表格，不画图）。
- E 组压缩次数、暂停次数照常列出。

## 5. 新指标：关键信息可见率

回答"省 token 的同时有没有丢信息"。不需要真模型，只做文字匹配，结果可复现。

- 剧本新增可选字段 `facts: { id: string; marker: string; step: number; audience: string[] }[]`：
  - `marker` 是一段独特的文字（如 `MAX-5MB-UPLOAD`），必须出现在第 `step` 步引入它的文本中（人类消息、回复或工具参数）；
  - `audience` 是需要知道这条事实的 Bot（`["*"]` 表示所有员工）。
- 机会：`audience` 中的 Bot 在第 `step` 步之后发出的每次剧本请求；额外请求不计（Bot 不做事）。
- 命中：该次请求的完整上下文文本包含 `marker`。
- 指标：每组的可见率 = 命中 / 机会（机会为 0 时输出 `n/a`），以及未命中次数；报告另列每条事实在各组的可见率。
- 校验：`marker` 必须出现在第 `step` 步的文本中，`audience` 必须是员工或 `*`。
- E 组压缩后的摘要：假定摘要保留压缩前出现过的全部 marker（对 E 有利，对 C 保守），报告中注明。
- 覆盖：五个剧本都标注事实——标准剧本各 4–6 条，长剧本各至少 15 条，包含改需求、新约定、接口约定、失败记录四类。
- 记录：`CallRecord` 新增可选 `factsSeen?: string[]` 与 `factsMissed?: string[]`（只列该请求的机会）。

## 6. 不做

- 项目板只追加的渲染方式（等长剧本结果出来再决定）。
- 真模型。
