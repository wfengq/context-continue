# 核心库：审查/拆分上下文与简报共用可缓存前缀

- 日期：2026-11-04
- 状态：已实现
- 上游：`2026-11-02-core-visibility-gaps.md` 第 5 节（后续第 1、2 项）、`2026-10-11-group-context-layer-design.md` 第 4、5.2 节

## 1. 问题

简报的段为 `common, memory, workspace, board, projection, delta, trigger`（前 4 段可缓存）。审查与拆分上下文只有 `common, board, projection` 三段，项目板从第 4 段变成第 2 段。负责人在简报与上下文之间切换时，按逐段相同的前缀规则只有 `common` 能命中缓存。最终评审的早期估算：这部分在长剧本上约 15k 费用单位（C 组此前费用上升的约 1/4）；实测见第 5 节。

另外，审查/拆分上下文不接受触发原因，评测 C 组只能自己按核心库格式拼一个触发段，重复了核心库的渲染且不进统计。

## 2. 改法

- `buildReviewContext` 与 `buildPlanningContext` 返回的段改为：`common, memory, workspace, board, projection, trigger`。
  - `common`、`memory`、`workspace`、`board` 的文字与该负责人同一时刻的 `buildBrief` 逐字节相同，可缓存标记相同（true）。
  - `projection` 段是审查或拆分的正文（内容不变），不可缓存。
  - 新增可选参数 `{ trigger?: { reason, detail } }`，用核心库的 `renderTrigger` 渲染为最后一段（不可缓存）；不传时没有这一段。
  - `stats.bySegment` 与 `total` 包含全部段。
- 构建上下文仍不改变工作区（除已有的"丢弃待确认已看过条目"）；记忆、工作区只读。
- 向后兼容：方法签名只增加可选参数；段数变化写进设计文档与 README。

## 3. 评测

- C 组改为把触发原因传给核心库，删去自拼的触发段。
- 重跑五个剧本六组，报告 C 组前后对比（基线为本计划开始时的提交）。预期：C 组费用下降，可见率不变。
- 顺带改正上一份设计文档第 5 节的措辞（"C 现在高于 D/E"→"C 的费用现在高于 D/E"）与核心库 README 中"该 Bot 的待确认条目"（实际只丢弃负责人的）。

## 4. 不做

- 拆分上下文的增量去重、项目级事实、抽取方案（另立计划）。

## 5. 结果

重跑五个剧本六组（基线为 664eeb5 之前的提交），只有 C 组变化，A/B/D/E/F 不变。

- C 组长剧本费用（合并）：324,779.7 → 321,190.8，-1.1%。
- C 组标准剧本费用（合并）：48,799.8 → 47,291.2，-3.1%。
- 可见率不变：长剧本 66.9%，标准剧本 37.1%。
- 输入 token 约增加 1%：审查/拆分上下文现在也带记忆与工作区两段。
- 107/107 个审查/拆分上下文的前四段与同一时刻负责人简报的前缀逐字节相同。
- 与 D/E 比较：标准剧本上 C 的费用仍高于 D/E；长剧本上 C 低于它们。

**为什么只省了约 3.6k，而不是估算的 15k**：基线里项目板已经被相邻的上下文共用缓存了。负责人很少在简报与上下文之间切换（长剧本 app 10 次，event 4 次），连续的上下文本来就共用 `common` 与 `board` 的前缀。剩下的前缀中断来自项目板本身的变化，多数是负责人自己的审查产生的（状态变更、新增约定）。若项目板不再变化，长剧本 app 上最多还能再省约 11.8k，但这不是对齐段落能解决的。

后续（另立计划）见 `2026-11-02-core-visibility-gaps.md` 第 5 节剩余各项。
