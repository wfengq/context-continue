## 1. 结论

**三个项目各自已经做了我们设计里的一部分，但没有一个做了"按项目结构给每个 Bot 计算投影"这件事。**

| 我们设计里的部件 | Munder Difflin | DeepSeek Harness Agent Team | DeLM |
|---|---|---|---|
| 只追加日志 | ✅ `log.jsonl` | ✅ 写在负责人会话日志里 | ✅ SQLite 事件日志 |
| 共享层 | ⚠️ `board.md` 自由格式 + `tasks.json` 看板 | ⚠️ 只有任务板（依赖、负责人、版本） | ⚠️ 任务队列 + FACT/FAIL 笔记 |
| 结构化项目知识（带理由的决定、接口约定、约定） | ❌ | ❌ | ⚠️ 只有 FACT/FAIL 笔记（带 scope、basis） |
| 私有层 | ✅ 每个 Agent 的 `identity.md`、`memory.md` | ✅ 每个队友有自己的会话 | ✅ 每个 Agent 有自己的工作目录 |
| 单一写入者 | ✅ 总控 Agent 是 `board.md` 唯一写入者，其他人只能提议 | ✅ 任务修改带版本号比对，过期的被拒绝 | ✅ 由服务端写入 |
| 增量更新 | ⚠️ 收件箱 + 游标 | ⚠️ 等待团队变化 | ✅ **"自上次读取以来的变化"，已读条目只显示 id 和状态** |
| 交付物按引用传递 | ❌ | ❌ | ✅ 只显示文件名和大小，需要时按 id 拉取 |
| **按每个 Bot 的相关性裁剪** | ❌ 每人读全部 `board.md` | ❌ | ❌ 每人看到所有变化（只是压缩了） |
| **由项目结构驱动唤醒** | ❌ 收件箱有消息才唤醒 | ❌ 收到消息或任何团队变化 | ❌ 任何同伴条目 |
| 负责人 + 人确认拆分 | ⚠️ 总控 Agent 自主，关键事项问人 | ⚠️ 负责人控制，没有人确认环节 | ❌ 去中心化，没有负责人 |
| 做成与宿主无关的组件 | ❌ Electron 应用 | ❌ 内置于 DSH | ⚠️ 另有 Codex / Claude Code 插件 |
| 防止 Agent 互相刷屏 | ✅ 跳数上限 + 只有请求类消息需要回复 | — | — |
| token 控制 | ✅ 每个 Agent 的预算 + 熔断器 + 记忆压缩 | ⚠️ 依赖通用的压缩机制 | — |
| 公开的对比数据 | ❌ | ❌ | ✅ 和单 Agent 比（编程任务） |

**仍然属于我们的差异点**（读完代码后确认）：
1. **结构化的项目知识**：带理由和被否决方案的决定、工作块之间的接口约定、全局约定，每条都标明影响哪些工作块。
2. **按 Bot 裁剪的投影**：每个 Bot 只拿到与自己工作块相关的部分。三个项目都是"人人看全部"。
3. **由项目结构驱动唤醒**：决定变了、接口变了、上游交付了，才唤醒相关的人。
4. **与宿主无关的库**，以及**项目形态任务上的对比数据**（和全量广播比、和单 Agent 比）。

## 2. Munder Difflin（9.2k⭐，TypeScript，Electron）

**设计文档**：`HIVE.md`；**主要代码**：`src/main/hive.ts`（3,669 行）、`reflect.ts`、`breaker.ts`。

### 它怎么做
- 磁盘上的 "hive" 目录：`registry.json`（名册）、`board.md`（自由格式的共享计划）、`tasks.json`（看板：todo/doing/blocked/done、负责人、优先级、依赖）、`log.jsonl`（事件流），以及每个 Agent 一个目录（`identity.md`、`memory.md`、`inbox/`、`outbox/`、`cursor.json`）。
- 每个 Agent 是一个长期运行的 `claude` CLI 进程。启动时用 `--append-system-prompt` 注入一段协议说明，**要求 Agent 自己用工具去读** `memory.md` 和收件箱。上下文是 Agent 自己"拉"的，不是系统算好"推"给它的。
- 消息采用"言语行为"字段：request / inform / propose / query / agree / refuse / done。只有 request、query、propose 需要回复；每次回复跳数加一，超过上限就交给总控 Agent，防止两个 Agent 无限来回。
- 总控 Agent（"Michael"）负责名册、路由、日常裁决，是 `board.md` 的唯一写入者；花钱、破坏性操作、范围变化、无法调和的冲突才交给人。
- **记忆压缩**（`reflect.ts`）：`memory.md` 超过约 128 KB 时，用 Haiku 改写成三段——置顶的长期事实（不动）、滚动摘要、最近 K 段原文。先备份、再校验、最后原子替换；压缩用的提示词保持字节不变以命中缓存。
- **熔断器**（`breaker.ts`）：检测重复调用同一工具、错误风暴、花费过快，按"提醒 → 限制 → 停止"逐级处理。

### 和我们的区别
- `board.md` 是自由格式的 Markdown，没有决定、接口约定这类结构，也就**没法按 Agent 裁剪**。
- 每个 Agent 的会话历史本身持续增长，依赖 Claude Code 自带的 `/compact`。
- 和 Claude Code 等 CLI 及 Electron 应用深度绑定，偏编程场景。

### 值得借鉴
- 言语行为 + 跳数上限，防止 Bot 互相刷屏。比我们设计里"一条人类消息最多 6 个回合"更细。
- 三段式记忆压缩及其"备份 → 校验 → 原子替换"的安全流程，可以直接用于我们的长期记忆和工作区笔记。
- 熔断器和每个 Agent 的 token 预算。
- 给人的确认请求写成短 Markdown、先说要什么——我们的"拆分确认"也该这样。

## 3. DeepSeek Harness（26.4 万⭐，TypeScript，插件架构）

**相关代码**：`packages/experimental/agent-team`、`packages/experimental/tool-agent-team`、`packages/core/system-prompt`、`docs/capability-seams.md`。

### Agent Team 怎么做（实验性）
- 一个负责人 + 命名的队友。队友可以**全新开始**（不带负责人的历史），也可以**分叉**（复制一份负责人已完成的对话）。只有负责人能创建和中断队友。
- **共享任务板**：任务有标题、详情、依赖、负责人；依赖全部完成才能认领；每次修改带版本号比对，过期的修改被拒绝；可以声明"将修改哪些文件"，两个进行中的任务范围重叠时发出警告。
- **私信**：每条消息作为一条用户消息追加到目标 Agent 的历史里。README 自己写明了 token 影响：每次投递都会把消息内容加进对方的历史。
- 任务板和名册的变化**不进入模型的对话历史**，只在调用工具时以结果形式出现。
- 已知限制：所有成员共用一个工作目录；不会自动释放任务负责人；没有嵌套团队。

### 能否在它上面做插件：可以
- `ctx.systemPrompt` 允许插件**只给某个 Agent** 添加提示词片段和动态上下文，**每一步都会重新读取**。这正是放我们 `buildBrief` 输出的位置。片段有 `order` 参数，可以把可缓存的部分排在前面。
- `ctx.tools` 可以注册我们的工具（`proposeDecision`、`promote` 等）。
- `ctx.agentTeams` 已经提供了名册、任务依赖和私信，我们的适配器可以**直接复用**它的任务板，只补上项目知识（决定、接口约定、约定）和投影。
- `ctx.compaction` 是可替换的，必要时可以接管压缩策略。

### 和我们的区别
- 没有项目层面的共享知识，只有任务。
- Agent 之间靠私信传递信息，每条都进对方的历史，这正是 token 增长的来源之一。

## 4. DeLM（斯坦福，论文 arXiv 2606.10662，Python）

**相关代码**：`board/shared_context.py`（639 行）、`prompts/prompts_n2.py`。

### 它怎么做
- 共享上下文是一个只追加的事件日志，条目类型：状态、任务项、认领、完成、笔记（FACT 或 FAIL，带 scope 和 basis 字段）。
- Agent 通过一个命令行工具读写，读取时可以等待同伴的新条目（最长 25 秒）。
- **增量视图**（`served()`）：每次读取返回"进行中的任务 + 自上次读取以来的变化"。已经看过的任务只显示 id、标题、状态、负责人，不再重复描述；需要完整内容时显式读取全部。
- **交付物按引用**：完成或笔记可以附带文件，但读取时只显示文件名和大小，需要时按 id 拉取或直接应用到自己的工作目录。
- 每个 Agent 都在自己的工作目录里产出一份**完整解答**，同伴的发现只是参考。
- 公开了 720 条运行轨迹，并提供 Codex / Claude Code 插件（`Decentralized-LM/delm-agent-plugin`）。

### 和我们的区别
- 没有负责人，也没有人参与；面向一次性的基准任务，不是持续的项目。
- 每个读者看到的是**全部**变化（只是压缩了），没有按相关性过滤。

### 值得借鉴
- "已读条目压缩显示"和"交付物按引用、按需拉取"——可以直接用在我们简报的第 4、6 段。
- FAIL 笔记：明确记录"试过但不行"的结论，对应我们决定里的"被否决方案"，但更通用，值得作为单独的条目类型。
- 它的论文结论是中心化调度会成为瓶颈。我们的负责人 Bot 只做判断，不转发内容，这一点要坚持。

## 5. 对设计的建议修改

1. **定位收窄**：核心库专注于"项目知识模型 + 投影计算 + 结构驱动唤醒 + 增量视图"。消息传递、任务依赖、版本校验这些宿主已经有的，由适配器映射到宿主的实现，不自己重做。
2. **第一个适配目标改为 DeepSeek Harness**：插件接口正好合适，生态最大，Agent Team 正缺项目知识层。OpenClaw 放第二，Munder Difflin 可以考虑给它贡献"结构化黑板"。
3. **借鉴的细节**加入设计：
   - 言语行为 + 跳数上限（来自 Munder Difflin）；
   - 三段式记忆压缩及安全流程（来自 Munder Difflin）；
   - 已读条目压缩显示、交付物按引用（来自 DeLM）；
   - FAIL 笔记作为单独的条目类型（来自 DeLM）；
   - 文件修改范围重叠警告（来自 DSH）。
4. **评测增加一组 DeLM 式的去中心化对照**，否则无法回应"为什么要负责人"。
5. 设计文档增加"相关工作与差异"一节，引用本文。
