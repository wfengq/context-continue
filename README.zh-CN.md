# context-continue

[English](README.md)

为多个 AI Bot 协作同一个项目提供共享的结构化项目上下文，并附带一套评测，把它与现有多 Bot 产品共享上下文的方式做对比。

多个 Bot 在群聊里做同一个项目时，通常每个 Bot 每一轮都要重读整段对话。本仓库验证另一种做法：项目维护一块小的**项目板**（目标、约定、工作块、接口约定、决定、事实、失败记录），每个 Bot 拿到一份**简报**——项目板中与它有关的部分，加上它上次之后的变化——以及它自己的私有笔记和记忆。

> **状态：实验中。** 下面的数字全部来自脚本化的假模型，只衡量各方案发送了多少上下文，不衡量 Bot 把事情做得好不好。

## 评测

六组跑同样的剧本。每次请求记录输入 token 数，以及其中可以命中提示缓存的部分（与该 Bot 上一次请求逐段相同的最长前缀；缓存命中按 0.1 计费）。

| 组 | 策略 |
|---|---|
| A | 一个 Agent 带完整历史完成全部工作（也代表 Muse、Duet 这类单个个人 Agent）。是对照基线，不是多 Bot 方案。 |
| B | 群聊，每条消息所有 Bot 都重读整段聊天（按公开描述近似 Grok 式 Bot 群）。 |
| **C** | **本项目：`@context-continue/core` 的简报。** |
| D | 共享的只追加日志，每个 Bot 读新增部分（DeLM 式）。 |
| E | 轮流发言的群聊，看最近消息窗口并带冻结的群组记忆（按 DS Bot `f823773` 源码近似）。 |
| F | 共享文档页面加各 Bot 自己的历史（按公开描述近似 Dots + Space）。 |

共六个剧本：三个标准剧本（20–40 步）、两个长剧本（160–164 步，6–8 个 Bot，包含中途改需求、审查打回、重新拆分）和一个超长剧本（1,154 步，8 个 Bot，六个发布周期）。每个剧本标注了关键事实（改需求、约定、接口约定、失败记录）以及哪些 Bot 需要知道；**关键信息可见率**指 Bot 干活的请求中，上下文确实包含它需要的那条事实的比例。

### 长项目模式

核心库还有一个可选的**长项目模式**（[`packages/core`](packages/core/README.md#long-project-mode-stream-mode)）：每个 Bot 不再每次拿一份新简报，而是一条只追加的流（先是整个项目板的快照，之后只追加新内容），除了追加的尾部都能命中提示缓存；追加超过 8,000 token 后，下一次请求发新快照。`auto` 模式下，项目的账本达到 `autoAfterEntries` 条时切换到流；缺省值 **75** 由本评测选定。评测把每个 Bot 自己的回复与工具调用按 E 组的作者格式放回它的流里，与 D、E 的历史一样。

| 剧本 | C 组设置 | 费用单位 | 比 D / 比 E | 关键信息可见率 | 上下文中位数 | 最大请求 |
|---|---|---:|---|---:|---:|---:|
| 标准 | 简报（默认） | 55,852 | +39.5% / +36.8% | 80.0% | 709 | 1,310 |
| 标准 | 从头使用流 | 63,441 | +58.5% / +55.4% | 95.7% | 1,425 | 7,748 |
| 标准 | **auto（75）**：不切换 | **55,852** | **+39.5% / +36.8%** | **80.0%** | **709** | **1,310** |
| 长 | 简报（默认） | 400,723 | +5.8% / +10.8% | 79.9% | 1,549 | 3,024 |
| 长 | 从头使用流 | 371,766 | −1.8% / +2.8% | 99.9% | 4,356 | 10,911 |
| 长 | **auto（75）**：第 60 步起 | **355,195** | **−6.2% / −1.8%** | **96.9%** | **2,498** | **10,598** |
| 超长 | 简报（默认） | 3,584,041 | −51.9% / −46.9% | 63.5% | 4,236 | 6,718 |
| 超长 | 从头使用流 | 2,025,560 | −72.8% / −70.0% | 99.8% | 9,806 | 18,721 |
| 超长 | **auto（75）**：第 123 步起 | **2,055,507** | **−72.4% / −69.5%** | **99.1%** | **9,778** | **18,943** |

D、E 供对照：标准 40,024 / 40,820（95.7% / 95.7%），长 378,684 / 361,692（98.1% / 97.7%），超长 7,452,381 / 6,747,043（100.0% / 99.2%）。

为什么是 75：标准剧本结束时账本有 42–44 条，所以一直使用简报；长剧本大约在三分之一处达到 75。取 50 或 60 结果相近，但离标准剧本的余量更小；取 100 时长剧本可见率降到 93.4%，费用高于 E；取 400 时长剧本根本不切换。长剧本上 `auto` 比从头使用流更便宜，因为项目早期简报比流小，但切换之前会漏掉简报漏掉的内容。

此表的说明：假模型只衡量上下文，不衡量 Bot 是否用上了这些信息；流中包含 Bot 自己的输出（不带会更便宜）；被重新拆分撤下的接口约定按设计在流中保持可见（超长剧本上核心库比原型贵约 15%，主要来自撤下的接口约定），剧本也把它们算作 Bot 仍需知道的事实；没有模拟真实的缓存过期，Bot 空闲超过供应商的缓存寿命时，下一次请求要整段重新计费；评测每步写入账本的条目比"把每条 Bot 回复都记为聊天"的宿主少，那样的宿主会更早达到 75（在这些剧本上，即使把脚本里每条 Bot 回复都记为聊天，也只到约 65 条，仍略低于 75；近似值）。详见[规格第 5 节](docs/superpowers/specs/2026-11-06-core-stream-mode.md)。

## 结论

1. **单次请求的上下文小，增长缓慢。** 长剧本上 C 组请求中位数约 1.5k token，最大约 3k；其他组最大的请求达到 14–27k。超长剧本上 C 组中位数约 4.2k、最大约 6.7k，其他组随历史增长到 7.1 万–19 万。这对上下文窗口限制、延迟和长项目有意义。
2. **C 组是否更省取决于项目长度。** 有提示缓存时，只追加的聊天历史几乎全部命中缓存，所以在标准与长剧本上 D、E 和 C 一样便宜甚至更便宜。C 组每次重新生成简报，项目板一变，从它开始往后的缓存都会失效。长剧本上 C 组费用约为 B 组的 1/5、F 组的 1/3，但不低于 D、E（标准剧本上还高于两者）。在这个超长剧本上其他组的请求随历史不断变大，C 组是六组中最便宜的，可见率为 63.5%（见第 3 点）：约为 D、E 的一半，F 的 1/3，B 的 1/14，A 的 1/3（A、B 仅在窗口无限的假定下成立，见局限）。E 组只压缩了一次，所以它被压缩封顶后的状态（请求大小稳定在阈值附近、费用线性增长）没有测到。
3. **按相关性裁剪是真实的取舍。** 每个 Bot 只看自己那部分，简报才能保持小；这也正是 C 组漏信息的原因：改需求只传到部分 Bot、接口约定看过一次就被折叠、记在别的工作块上的失败记录看不到。超长剧本上 C 组可见率降到 63.5%（长剧本 79.9%）：项目板只保留最近 20 条人类消息，四条较早的改需求被更新的消息挤出后就漏看；接口约定与失败记录的可见率也比长剧本更低。
4. **把项目级事实放上共享项目板能补回可见率，代价可以量化。** 全部打开时 C 组能看到 96% 的关键事实，接近 D、E，长剧本费用比全部关闭高约 57%。多出的费用来自更大的项目板每次变化都要整段重发，调整缓存顺序消除不了。
5. **有些事实需要 Bot 配合。** Bot 之间只在聊天里约定、没有记录成接口约定的内容，永远到不了项目板。
6. **长项目上，只追加的流比每次重建简报更好。** 长项目模式（`auto`，账本 75 条时切换）下，C 组在长剧本与超长剧本上比 D、E 便宜（分别约 2–6% 与约 70%），可见率 96.9%（长剧本上略低于 D、E 的 98.1% / 97.7%）与 99.1%；标准剧本仍使用普通简报，在那里用流会更贵。它的请求比简报大（超长剧本上最大约 1.9 万 token），仍约为 D、E 的 1/5。

## 局限

- 脚本化假模型：不衡量任务质量、前后矛盾，也没有真实的摘要。
- B、F 按公开描述近似闭源产品；E 按 DS Bot 源码近似。
- E 组的压缩只被边缘地测到：超长剧本上 E 组只压缩一次，只有负责人，发生在第 1,006 步，此后只剩约 150 步，历史超出阈值不到 1%；这段历史近一半（约 46%）是负责人自己的重新拆分（由仓库外修改过的诊断副本测得，见规格 §6.3）。压缩后负责人的可见率依赖"摘要保留全部事实标记"的假定（去掉标记，剩余步数中由 100% 降到 49%；由仓库外修改过的诊断副本测得，见规格 §6.3）。
- 只有 E 组模拟上下文窗口，其他组的数字假定窗口无限：超长剧本上 A、B 超过 128,000 token，D 最大约 12.5 万。
- 关键信息可见率按标记文字匹配，换了说法的事实算作漏看。
- 所有组都没有计入工具定义。

每次评测报告末尾都会列出完整的说明。

## 复现

需要 Node.js 22.5+ 和 pnpm。

```sh
pnpm install
pnpm test                                    # 核心库与评测的测试
pnpm -C packages/bench bench run --scenario all --group all --out results --stamp T
pnpm -C packages/bench bench run --scenario all --group C --c-public all --out results --stamp all
pnpm -C packages/bench bench run --scenario all --group all --c-stream auto --out results --stamp auto   # 长项目模式
```

同样设置运行两次，`results.json` 与 `report.md` 逐字节相同。全部选项见 [`packages/bench/README.md`](packages/bench/README.md)。
